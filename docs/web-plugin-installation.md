# Webからのプラグインインストール

Webの `/plugins` と `/en/plugins` に一覧・検索・種類別フィルターを用意する。各ボタンは以下のURLを開く。

```text
notyra://plugins/install?repo=yuma-shin%2Fnotyra-plugins&id=notyra-theme-blue
```

## 利用フロー

1. Webで「Notyraにインストール」を選ぶ。
2. ブラウザーの確認からNotyraを開く。
3. 設定ウィンドウのプラグイン欄に、プラグインIDとGitHub配布元が表示される。
4. 「インストール内容を確認」を押す。既存のPluginManagerが、そのIDの配布ZIPを取得・検証する。
5. 既存の同意ダイアログで、作者・取得元・権限・通信先を確認してインストールする。

初回のサードパーティ注意事項を確認するまでは、取得・インストールを始められない。追加権限がない場合も同意を省略しない。失敗・同意のキャンセル時は要求を残し、再試行または明示的なキャンセルができる。成功した要求だけ自動で一覧から取り除く。

URL対応は今回追加したアプリから利用可能。既に公開済みのv4.0.0にはハンドラーがないため、アプリの次回リリースが必要。サイトはブラウザーからインストール状態や起動成功を検出したと断定せず、対応版のダウンロードとアプリ内導入手順を案内する。

## 実装

- Tauri公式deep-linkプラグインに `notyra` スキームを登録する。single-instanceを最初に初期化し、`deep-link` featureで既存プロセスに引き渡す。
- RustでURLのscheme・host・path・queryを検証する。`repo` と `id` はそれぞれ必須で、重複・未知のパラメータ・認証情報・port・fragment・任意のZIP URLを拒否する。
- 許可する配布元はGitHubの `owner/repo`。プラグインIDは既存の検証規則に従う。
- 最大10件のメモリ内キューに保持する。同じ配布元とIDを重複させず、起動中・設定WebViewの読み込み前でも要求を失わない。確認済みのrequest IDだけを取り除く。
- 設定ウィンドウは通知の購読後にキューを読み、通知と初期応答の前後が逆転しても古い応答を無視する。
- リンクのIDを `installFromRepo(repo, expectedId)` に必ず渡す。複数プラグインを同じReleaseで配布していても、選択したテーマが既定のToCに置き換わらない。
- macOS・Windowsのインストーラーでスキームを登録する。LinuxはAppImageの移動も考慮して起動時に再登録する。Windows開発ビルドは既存の関連付けを上書きしない。

Tauriの設定・起動時と起動中のイベント・single-instance連携は[公式ガイド](https://v2.tauri.app/plugin/deep-linking/)に基づく。

## 検証

- Rust: URLの正常系、不正な入力、ID保持、要求の重複排除、キュー上限、古いackの無視、再試行。
- React: 初回警告、選択したIDの取得、同意前にインストールしないこと、キャンセル時の保持、成功後の解除、起動時・起動中の要求、古い応答の無視、購読解除。
- Web: 一覧の検証、不正な取得元・IDの拒否、全5プラグインのリンクの整合性。

OSからの実際の起動・関連付けは、各OSの対応版アプリをインストールして確認する。ブラウザーの「アプリを開く」確認は利用者が操作する。

Windowsで型チェック、Viteビルド、Rustの全175件、clippy（警告をエラー扱い）、フロントエンド142ファイル・1,160件が成功。Webの本番ビルドとリンク検証2件、日英の一覧・検索・テーマ絞り込み・選択したテーマIDの受け渡し・未導入時の案内、幅390pxでの表示を確認した。OSからの実際のプロトコル起動は未確認。ブラウザー検証ではOSへの起動だけを抑止し、hrefとクリック後の案内を検証している。
